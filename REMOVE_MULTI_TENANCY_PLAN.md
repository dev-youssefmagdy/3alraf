# Remove Multi-Tenancy → Single Store (Master Plan)

Owner request (2026-11-06): remove multi-tenancy from the whole project. One store, one admin panel, one database (no `tenant_id`).
**The current tenant panel is the main panel: nothing in it may be removed.** Modules/pages that exist only in the central panel are ADDED to it.
Nothing may be missed: models, migrations, seeders, factories, commands, scheduler, jobs, events, listeners, notifications, broadcasting, cache keys, storage paths, policies, permissions, routes, middleware, views, lang, config, env, n8n, integration API, mobile API, Flutter app, WhatsApp Node service, deploy configs, tests, docs.

## 1. Target architecture (decisions; every agent follows these)
1. **One host.** `APP_URL` (local `http://3alraf.loc`). Admin panel = `/admin`, storefront = `/{locale}/...`, `/` → redirect to default locale. No subdomains, no `{tenant}` route parameter, no landing/"choose country" page, no "store unavailable" page.
2. **Store settings replace the tenant row.** Table `tenants` → `stores` (exactly one row, id 1). Model `App\Models\Store`. Helper `store(): Store` (never null, cached per request) replaces `current_tenant()`; `selected_tenant_id()`, `tenant_url()`, `tenant_slug_from_host()`, `central_domain()`, `central_url()` are removed (callers use `url()`/`route()`). Columns kept: name, country, currency_code/symbol, default_locale, locales, timezone, settings (encrypted JSON: payment creds, COD, growth flags, SEO…). `slug`, `is_active`, `currency_rate` dropped (or kept unused only if a calc needs rate=1 — ERP/report agents decide, and document it in CALCULATIONS.md).
3. **No `tenant_id` anywhere.** One forward migration `database/migrations/2026_11_06_000000_convert_to_single_store.php` (plus split files if large) that, for all 111 tables: drops FKs on `tenant_id`, drops indexes containing it, **recreates unique indexes without `tenant_id`** (e.g. `unique(tenant_id, slug)` → `unique(slug)`), drops the column. Must work on MySQL **and** the test DB driver (check `phpunit.xml`). It aborts with a clear message if `tenants` has more than 1 row. `down()` throws (restore from the backup instead). Old migrations are NOT edited (safe for any deployed DB; fresh installs create then drop).
4. **One admin account type.** `tenant_admins` → `admins`, model `App\Models\Admin`, guard + provider `admin`. Central admins are merged in (same email → keep one account, union of roles). Spatie: all roles/permissions move to guard `admin`; same-named roles are merged; the central-only permissions (catalog, languages, AI providers/models/usage, store settings (was tenants), erp central monitoring) are added to the single permission list (`config/permissions.php` + `PermissionSeeder`); Super Admin gets all.
5. **Polymorphic / class-name data is rewritten in the migration**: `App\Models\TenantAdmin`, `App\Models\CentralAdmin`, `App\Models\Tenant`, `App\Models\TenantProduct(Variant)`, `App\Models\AiTenantSetting` in `model_has_roles`, `model_has_permissions`, `notifications`, `activity_log`, `personal_access_tokens`, `images`, `qr_codes`, `admin_otps`, etc. (find every `*_type` column and every morph map).
6. **Naming cleanup (no "tenant" left in code).**
   | Old | New |
   |---|---|
   | `Tenant` / `tenants` | `Store` / `stores` |
   | `TenantAdmin`, `CentralAdmin` / `tenant_admins`, `central_admins` | `Admin` / `admins` |
   | `TenantProduct`, `TenantProductVariant` / `tenant_products`, `tenant_product_variants` | `StoreProduct`, `StoreProductVariant` / `store_products`, `store_product_variants` (FK columns `tenant_product_id` → `store_product_id`) |
   | `AiTenantSetting` / `ai_tenant_settings` | `AiSetting` / `ai_settings` |
   | `App\Http\Controllers\Tenant\*`, `Central\*` | `App\Http\Controllers\Admin\*` |
   | `resources/views/tenant`, `resources/views/central` | `resources/views/admin` |
   | route names `tenant.*`, `central.*` | `admin.*` (storefront keeps `storefront.*`, API keeps `api.v1.*`) |
   | `routes/tenant_admin.php` + `routes/central.php` | `routes/admin.php` |
   | `config/tenancy.php` | `config/store.php` |
   | `TenantRepository(Interface)`, `TenantService`, `TenantData`, `TenantDataTable`, `AiTenantDataTable`, `TenantProductDataTable`… | removed or renamed Store* |
   | env `APP_CENTRAL_DOMAIN`, `TENANT_SEED_DEFAULTS`, `SESSION_DOMAIN=.domain` | removed / `STORE_SEED_DEFAULTS` / `SESSION_DOMAIN=null` |
   Exceptions allowed: historical migration files, the conversion migration, docs that describe the history.
7. **Products.** Keep both layers: `products` (master catalog: attributes, variants, barcodes, categories) and `store_products` (price/sale/cost/status, what the Catalog page edits). The Products CRUD from central is added to the panel; Products and Catalog pages link to each other ("List in store" / "Edit master product"). Merging both into one table is a possible later step, not this project.
8. **APIs stay backward compatible.** `/api/v1/*` registered once, no tenant. `X-Tenant` header and `{slug}.domain` hosts are ignored. `GET /api/v1/tenants` stays as a deprecated alias returning the single store (old app builds keep working). `app-config` returns the store (currency, locales, country). Integration API (n8n): client token no longer carries a tenant; event payloads drop `tenant`/`tenant_id` fields (keep a `store` object if a flow needs currency/locale).
9. **WhatsApp:** one owner. `owner_key`/`tenant_id` ownership removed; one session; broadcast channels `whatsapp` and `whatsapp-chat` (guard `admin`); Node gateway session id becomes a single fixed id (accept old ids for compat).
10. **Storage/media:** existing file paths in the DB stay valid (do not move files). New uploads drop any `tenants/{id}/` prefix. Cache keys drop tenant prefixes; run `php artisan optimize:clear` + cache flush at the end.
11. **Layering rules stay** (Controller → FormRequest → DTO → Service → Repository → Model, enums, Blade components, Tailwind, toastr, Yajra). Read `backend/docs/CALCULATIONS.md` before touching orders/discounts/shipping/fees/commission/refunds/stock valuation/reports, and update it where rules change (central currency normalisation goes away).

### 1.12 Lead rulings after Phase 1 (override anything above that conflicts)
- **Migration file name** `2026_12_31_000000_convert_to_single_store.php` (existing migrations run up to `2026_12_18`; it must run last). Split files use `2026_12_31_00000N_*`.
- **Admin merge key = phone** (admins have no email; login is phone + OTP). Same phone → one account, union of roles.
- **WhatsApp:** keep session id `central` (it is the connected one; the phone must not re-scan the QR code). Its conversations/settings win the merge; the disconnected tenant session's rows are merged under it or dropped if duplicate.
- **Legacy subdomain hosts:** add a permanent `301` for `{any}.APP_HOST/*` → `APP_HOST/*` (same path + query), so printed QR codes, affiliate links, sent mails and old app builds keep working. Payment/webhook POST routes (`webhooks/*`) and `/api/*` are **served directly** on legacy hosts (no redirect). This is the only allowed subdomain code, in one clearly named middleware/route file (`LegacyHostRedirect`).
- **Permissions:** `ai_tenants.*` → `ai_platform.*`; `tenants.view/edit` → `store_settings.view/edit`; `erp_central.*` dropped (Anomalies page uses `erp.audit.view`); role `tenant-owner` → `owner`.
- **OTP:** keep today's behaviour per account (the merged super admin keeps the central account's OTP bypass); no new security behaviour.
- **Timezone:** set once at boot from `store()->timezone` (AppServiceProvider), not per request.
- **AI & Growth on/off switches** live on the Store Settings page (always reachable), never only on pages hidden by `ai.enabled` / `growth.enabled`.
- `DatabaseSeeder` seeds one store.

### 1.13 Owner ruling 2026-11-06 (overrides §1.2, §1.6, §1.7 and every "Store*" name above)
- **No `Store`, `StoreProduct`, `StoreProductVariant` (or any similar wrapper) anywhere.** Use `Product` and `ProductVariant` directly.
- **Listing data merges into the catalog tables:** `tenant_products` columns (`price`, `sale_price`, `cost`, `min_stock_alert_qty`, `content`, `gift_occasions`, `gift_recipients`, `gift_suitable`, listing `is_active`) move onto `products`; `tenant_product_variants` columns (`price`, `sale_price`, `cost`, `min_stock_alert_qty`, `is_active`) move onto `product_variants`. `products.is_active` = master active AND listing active; a product with no listing row → `is_active = 0`, price NULL. Then `tenant_products` / `tenant_product_variants` are dropped. Every reference (FKs, `tenant_product_id` columns, polymorphic rows such as `qr_codes`/`images`/`activity_log` pointing at `App\Models\TenantProduct` ids, cart/order/bundle/flash-sale/list/custom-page items, JSON) is remapped to the matching `products.id` / `product_variants.id`.
- **Catalog page stays** (owner: nothing removed from the panel) but edits `products` directly (price/sale/cost/status/QR); its "available/bulk enable" flow becomes "activate products". The Products CRUD page also shows the price fields.
- **Store-wide settings** (former tenant row: name, country, currency code/symbol, default_locale, locales, timezone, encrypted settings JSON: payment creds, COD, SEO, growth/AI flags, …) live in a generic key-value **`settings`** table (`App\Models\Setting`, helper `setting(string $key, $default = null)`, secrets encrypted), not in a "store" entity. Admin page name: **Settings → General**. `tenants` table is dropped after its values are copied into `settings`.
- `ai_tenant_settings` → `ai_settings` stays (it is AI config, not a store wrapper).
- Helper names: no `store()`; use `setting()`. Config file `config/tenancy.php` → its remaining keys go to `config/app.php`/`config/catalog.php` style files, not `config/store.php`.
