# Order & Reporting Formulas — SINGLE SOURCE OF TRUTH
**Any change to order, cart, discount, shipping, payment-fee, commission, refund, stock-valuation or report math MUST first re-read this file, update it if the rule changes, and keep `App\Services\Orders\OrderCalculator` + tests in sync.** Round half-up to 2 decimals at the END of each labeled step only.

**Single store (2026-11-06):** the project runs ONE shop with ONE currency, `setting('currency_code')` (Settings → General). Every amount below is in that currency; there is no cross-store aggregation, no base currency and no `currency_rate` conversion anywhere (orders keep their own `currency` column as a snapshot). "Settings" below = the site-wide `settings` table read through `setting()` (former per-store settings JSON); "listing" price/sale price/cost = `products` / `product_variants` columns.

## Definitions (per order, shop currency)
- `unit_price` = effective price at order time = flash-sale price if active & qty available, else `sale_price` if set, else `price` (a variant with its own `price` uses its own `sale_price`; otherwise the product's price and sale price apply).
- `line_subtotal = unit_price × qty`
- `subtotal = Σ line_subtotal`
- `unit_cost` = cost snapshot (`product_variants.cost` override, else `products.cost` = weighted-average cost from purchases). `line_cost = unit_cost × qty`; `cogs = Σ line_cost`.
  **Re-valued at shipment (2026-11-04, ERP-002):** when the order ships, each line's `unit_cost` becomes the cost the stock ledger actually removed (the `sale_out` movement = shipping branch's weighted average at that moment; a movement with cost 0, e.g. uncosted backorder stock, keeps the snapshot) and `cogs` is recomputed; `net_profit` is recomputed in the same status change. Returns (`returned_cogs`, `return_in`) therefore reverse at the shipped cost.

## Order totals (apply in this exact order)
1. **Discount** (single code per order): code scope base `B` = subtotal of eligible lines (all lines if scope=all).
   - percent: `d = B × pct/100`; fixed: `d = min(value, B)`.
   - `discount = min(d, max_discount_cap if set else d)`; requires `subtotal ≥ min_order`.
   - Free-shipping codes: `discount = 0` on goods, `shipping_discount = shipping` (step 2).
   - Discount is distributed to lines proportionally to `line_subtotal` (for returns/refund math): `line_discount = discount × line_subtotal/B` (eligible lines; last line takes the rounding remainder). **Bounds: `0 ≤ line_discount ≤ line_subtotal` always** (clarified 2026-10-25): each proportional share is rounded and clamped to `[0, line_subtotal]`; the remainder `discount − Σ shares` (positive OR negative, from rounding/clamping) is then moved cent-exactly onto eligible lines in order — a positive remainder only onto lines with room (`share < line_subtotal`), a negative one only off lines with `share > 0` — so Σ line_discount = discount exactly, no share is ever negative and no `return_value` is ever negative.
2. **Shipping** `shipping = price_list(company, city)`; if `subtotal − discount ≥ free_over` (when set) → 0. `shipping_discount` as above. `shipping_net = shipping − shipping_discount`. `shipping_cost` (what we pay the carrier) = `price_list.cost` if set else `shipping` (used in profit).
3. **Taxable/VAT**: setting `tax_rate` as a percent, e.g. 14 (default 0, `settings.prices_include_tax`, prices tax-exclusive unless `prices_include_tax`). with `r = tax_rate/100`: `tax = (subtotal − discount) × r` (if inclusive: `tax = (subtotal − discount) × r/(1+r)` and not added). Tax on returns: **exclusive** orders refund `tax_share = round(tax × return_value/(subtotal − discount))` on top of `return_value` (cap for the refund = `return_value + tax_share (+ shipping_net if refund_shipping)`); **inclusive** orders refund only `return_value` (tax is already inside it). Tax is always excluded from profit. **VAT is never revenue (clarified 2026-10-25):** `tax_in_goods = tax` when inclusive, else 0. An order is detected as inclusive from its stored columns: `tax > 0` and `total − (subtotal − discount + shipping_net + payment_fee_charged + cod_fee) < tax` (tax was not added on top). Tax portion of returned goods is CUMULATIVE per order (exact, no cent drift): for returns in `id` order with prior cumulative returned value `P` and this return's value `v`: `return_tax = round(tax × (P+v)/(subtotal − discount)) − round(tax × P/(subtotal − discount))` (returning everything ⇒ Σ return_tax = tax exactly). Exclusive: this is the `tax_share` refunded on top (P = Σ return_value of the order's already-REFUNDED returns); inclusive: it is the VAT inside `return_value`, removed from the profit reversal and the commission (P = Σ return_value of earlier approved/refunded returns).
4. **Payment fee**: base `F = subtotal − discount + shipping_net + tax(exclusive only)`; `fee = F × fee_percent/100 + fee_fixed`. If `fee_bearer = customer`: `payment_fee_charged = fee` and added to total; if `merchant`: `payment_fee_charged = 0` (fee still a merchant cost). COD: fee per method config (usually 0).
4b. **COD extra fee** (`cod_fee`, only when the payment method is COD and `settings.cod_extra_fee_enabled`; see "COD extra fee" below). Charged to the customer only when bearer = `customer`.
5. **Total**: `total = subtotal − discount + shipping_net + tax(excl.) + payment_fee_charged + cod_fee`.
6. `paid_amount`, `due = total − paid_amount`.

## Profit (per order, recognized once an ADMIN has confirmed the order — decision 2026-10-21)
An order counts in sales/profit only when status ∈ {confirmed, processing, shipped, delivered} (i.e. confirmed by an admin; `pending` = merely submitted by the customer and never counts). Bucketed by the order's `created_at` (order date), NOT the delivery date. Cancelled orders never count; a cancel after confirmation removes it (and its commission).
Confirmation rules: COD orders need admin confirmation; offline/wallet orders need the customer's proof-of-payment file AND admin approval of that proof before confirmation; online-gateway orders confirm automatically only after a verified webhook, then still sit as `pending` until admin confirms unless `settings.auto_confirm_paid_online` is on.
`revenue_goods = subtotal − discount − tax_in_goods` (VAT excluded; equals `subtotal − discount` for tax-exclusive orders)
`gross_profit = revenue_goods − cogs`
`order_net_profit = gross_profit + shipping_net − shipping_cost − payment_fee_total − affiliate_commission + cod_fee`
where `payment_fee_total = fee` (always, whoever bears it) and `+ payment_fee_charged` income is included: `order_net_profit += payment_fee_charged`. (So bearer=customer ⇒ fee nets to 0.) `cod_fee` (customer-borne COD extra fee) is merchant income exactly like `payment_fee_charged`: it offsets the carrier's COD handling cost, which is already inside `shipping_cost`. Merchant-borne COD fee ⇒ `cod_fee = 0` (nothing charged, nothing added; no extra cost is booked because the carrier's COD charge is part of `shipping_cost`). Tax is pass-through and excluded.
Period **Net Profit** = `Σ order_net_profit − Σ (return_value − return_tax_incl − returned_cogs) − Σ return_shipping_cost − Σ expenses` where the goods reversal `(return_value − return_tax_incl − returned_cogs)` counts ONLY returns whose order is in the sales set (status confirmed|processing|shipped|delivered) — a fully-returned order (status `returned`) is already out of `Σ order_net_profit`, so subtracting its returns again would remove it twice (fixed 2026-10-25); `return_shipping_cost` is a real cash cost never contained in any order profit and is subtracted for every approved/refunded return. `return_tax_incl` = `return_tax` for inclusive orders, 0 otherwise (expenses by date, optional branch). `refund_net_loss` is defined ONCE: **return shipping cost only** (the kept payment fee is already inside `order_net_profit`, never subtract it again).

## Payment methods & COD split (decision 2026-10-21, implemented sprint 10)
- Every payment method (COD, wallets such as Vodafone Cash / E& Cash / InstaPay / any admin-defined wallet, online: Paymob, FawryPay, …) has an independent `is_active` toggle; COD exists by default, cannot be deleted (may be deactivated). Checkout offers only active methods whose online driver is implemented.
- **COD**: with `settings.cod_collect_shipping_upfront` (default true) the customer prepays `prepaid_shipping = shipping_net` via an active online/wallet method (`orders.prepay_method_id`; wallet needs proof + admin approval, online needs a verified webhook) and the carrier collects the rest: `cod_amount = total − prepaid_shipping`. If `shipping_net = 0` nothing is prepaid. With the setting false: `prepaid_shipping = 0`, `cod_amount = total`. Non-COD orders: `cod_amount = 0`, `prepaid_shipping = 0`. The prepay leg carries NO extra fee (the fee config of the COD method applies to the order as before; gateway cost of the prepay leg is not modelled).
- **COD extra fee** (implemented; keys stored in the `settings` table, edited at admin "COD fees", perm `settings.view|edit`; ONLY `OrderCalculator::codExtraFee()` does the math). Settings: `cod_extra_fee_enabled` (bool, default false), `cod_extra_fee_type` (`fixed`|`percent`|`fixed_plus_percent`), `cod_extra_fee_fixed`, `cod_extra_fee_percent`, `cod_extra_fee_min` (floor, optional), `cod_extra_fee_max` (cap, optional), `cod_extra_fee_free_over` (optional), `cod_extra_fee_bearer` (`customer`|`merchant`), `cod_extra_fee_city_fixed` (map city_id → flat amount, optional), `cod_extra_fee_label` (translatable; default "رسوم الدفع عند الاستلام" / "COD fee").
  Order of evaluation (bcmath, round half-up at the end of each labeled step): (a) not COD or disabled ⇒ `0.00`. (b) `base F = subtotal − discount + shipping_net + tax(exclusive only)` (same base as the payment fee). (c) `raw = fixed` (type fixed) | `F × percent/100` (type percent) | `fixed + F × percent/100` (fixed_plus_percent), rounded. A per-city override for the order's city REPLACES `raw` entirely with that flat amount (and is not clamped by min/max). (d) otherwise `fee = max(raw, min)` if min set, then `min(fee, max)` if max set (max wins if min > max). (e) waived (`0.00`) when `free_over` is set and `subtotal − discount ≥ free_over` (also applies to city overrides). (f) bearer `merchant` ⇒ the computed fee is NOT charged: `cod_fee = 0`. bearer `customer` ⇒ `cod_fee = fee`, part of `total`, of `cod_amount` (the carrier collects it) and income in profit (`+ cod_fee`). It is NEVER part of `prepaid_shipping` (`prepaid = shipping_net` only; `cod_amount = total − prepaid`). Snapshotted per order: `orders.cod_fee`, `orders.cod_fee_label` (translations). Shown to customers (quote, order page, invoice, API `cod_fee`/`cod_fee_label`); profit/cost fields stay hidden.
  Returns: shipping (`shipping_net`, and the online-paid prepaid shipping leg) is refunded AT MOST ONCE per order: a later return with `refund_shipping` whose earlier sibling is already `refunded` gets no shipping in its refund cap and sends no shipping portion to the provider. The COD fee is NOT refunded (refund cap = `return_value + tax_share (+ shipping_net)`, unchanged); it stays in the order's profit. `ReturnService::taxShare` excludes `cod_fee` when detecting inclusive tax. Reports: cod-settlement `collected/in_transit/owed` use `cod_amount`, so the fee is included automatically; Net profit report adds a `COD fee` income line.
- `paid_amount` = money actually received (prepaid shipping once settled; COD cash is booked as paid on delivery, then `paid_amount = total`). `due = total − paid_amount`. Payment status `partially_paid` = prepaid shipping received, COD balance outstanding.
- **Carrier settlement report** (per shipping company, COD orders, order date): `collected = Σ cod_amount` of `delivered` orders (cash the carrier holds), `in_transit = Σ cod_amount` of `shipped` orders, `carrier_fee = Σ shipping_cost` of delivered orders, `owed_to_merchant = collected − carrier_fee`. "Mark carrier settled" (`orders.carrier_settled_at`, action on the report; permission `orders.payments`) moves delivered COD orders of one carrier + date range out of `collected`/`carrier_fee`/`owed` (outstanding only) and into `settled = Σ(cod_amount − shipping_cost)`; `in_transit` (shipped) is never affected.
- **Offline proof at checkout (2026-10-29)**: "offline" = WALLET type. The transfer proof file is now REQUIRED IN THE CHECKOUT REQUEST (multipart `proof`) for a WALLET payment method and for a WALLET prepay leg on COD (only when `prepaid_shipping > 0`); COD alone and online never need it. The order is created in the same transaction with `proof_status=pending`, `payment_status=review` (no money moves; `paid_amount` stays 0 until an admin approves). No amounts change. The file's sha256 is stored in `orders.payment_proof_hash`; a hash already attached to another non-rejected, non-cancelled order is refused (also on re-upload). Abuse limits: `config/checkout.php`.
- **Confirmation gates**: COD (upfront) needs the prepay settled (`paid`), wallet needs proof APPROVED (payment `paid`), online needs payment `paid` (verified webhook); then an admin confirms (or `settings.auto_confirm_paid_online` auto-confirms a paid ONLINE order). Approving a proof does NOT confirm the order.
- **Refunds** go through the provider for online payments; the order is marked refunded ONLY when the provider reports success (a failed refund leaves `refunded_amount`/status untouched and the return stays `approved`). Wallet/COD refunds are manual money moves.
- Soft-deleted discount codes and customers release their unique `code`/`email` (tombstoned `value#del{id}` on soft delete), so the same code/e-mail can be created again.
- Webhooks: signature verified with the provider scheme, then the provider is re-queried (Paymob transaction GET; FawryPay status/v2 — status, paid amount and reference must match the webhook, unreachable provider ⇒ rejected so the provider retries), then amount, currency, provider status and order reference are cross-checked against OUR order (mismatch rejected, nothing settled); each provider event is processed once (`payment_events` unique provider+event_id).

**`orders.net_profit` lifecycle**: `0` while `pending`; computed by `OrderStatusService` when an admin confirms (formula above from the stored order columns); after each approved return it is recomputed as `formula − Σ(return_value − returned_cogs + return_shipping_cost) + return_tax_incl(Σ return_value)` (VAT inside returned goods of inclusive orders is not profit, so it is not reversed) over the order's approved/refunded returns (commission already mirrored from the cumulative-returns rule); set back to `0` on cancel/fully-returned. The period Net Profit report keeps using the component formula (returns subtracted by return date), `orders.net_profit` is the per-order running figure used by the Sales report.

## Affiliate commission
Base = `revenue_goods = subtotal − discount − tax_in_goods` (goods after discount, excl. shipping and VAT — inclusive prices have their VAT removed; `affiliate_commissions.base`). Tier chosen by affiliate's **approved lifetime delivered sales amount** BEFORE this order (tier table: `min_sales → percent`, highest min ≤ sales wins). `commission = base × percent/100`. Tier basis (implemented): `lifetime sales = Σ revenue_goods − Σ (return_value − return_tax_incl)` of the affiliate's orders with status `delivered` (cancelled never count; **returns reduce lifetime sales and the commission**, decision 2026-10-21); tiers live in `affiliate_tiers`, none ⇒ 0%. Attribution: last-click cookie `aff` (30 days) set by `?utm_source=affiliate&aff={uuid}`; the order stores `affiliate_id`; self-referral (same email) and non-approved affiliates are ignored. One `affiliate_commissions` row per order (`base`, `percent`, `amount`).
Status: pending at order → approved by `affiliates:approve-commissions` (daily) once the order is `delivered` and `settings.affiliate_return_window_days` (default 14) elapsed → paid when admin marks the affiliate's payout paid. A payout request takes ALL approved, un-requested commissions (`amount` = their sum, recomputed at payment); rejecting it frees them again. Cancelled / fully returned ⇒ voided (amount 0). **Partial return — ONE formula, always recomputed from the cumulative returned value (no drift over several partial returns):** `commission = round((base − (R − return_tax_incl(R)), floored at 0) × percent/100)` with `R = Σ return_value of the order's approved/refunded returns` using the `base`/`percent` stored on the commission row; mirrored in `orders.affiliate_commission`. Paid commissions are never altered.

## Returns & refunds
- Return line: `return_value = (unit_price × qty_returned) − discount_share`, CUMULATIVE per line (clarified 2026-10-25): with `A` = units of the line already returned or pending in other requests, `discount_share = round(line_discount × (A+qty_returned)/qty) − round(line_discount × A/qty)`, so returning a line in several parts sums EXACTLY to `line_subtotal − line_discount` (the last unit takes the exact remainder) (never refund shipping unless whole order cancelled before shipping or `refund_shipping` flag).
- Concurrency (2026-10-25): request locks the order row and re-reads items; approve/refund lock the order row, then re-read the return row `FOR UPDATE` and re-check its status on the fresh row (a double click / parallel request can never restock twice or refund through the provider twice); approve also refuses when `returned_qty + qty > quantity` for any line.
- Stock: restocked (if `restock=true`) at the returned branch; add movement `return_in` at original `unit_cost` (= the shipped cost, see Definitions).
- **Cancel after shipment = returned to sender / failed delivery (2026-11-04, ERP-011):** `shipped → cancelled` is allowed for admins (never for customers: `OrderStatus::cancellableBeforeShipping`). The goods come back (`return_in` of every line at its `unit_cost`, `stock_deducted = false`), flash/discount usage is released like any cancel, the paid amount is refunded by the normal cancel rule, and the order leaves sales/profit (`net_profit = 0`). Carrier charges for the failed attempt are not modelled automatically (record them as a carrier bill / "Pay carrier").
- **Refund account (ERP ledger, ERP-001/010):** a refund is credited to the account the money is paid back FROM: the part sent back through the provider (`RefundService::onlinePortion`, stored as `order_returns.refund_online`) → Gateway; the rest → `order_returns.refund_from` chosen on the refund form (cash|bank|pos_cash|wallet|gateway|carrier_receivable), default: COD → cash, wallet → wallet, online → gateway, counter sale → POS cash; for COD-with-prepaid-shipping the refunded shipping leg comes out of the prepay method's account. Never the carrier receivable unless "refunded by the carrier before settlement" is chosen.
- `refund_amount` ≤ paid; the payment fee is NOT refunded (the merchant keeps bearing it; it stays inside the order's profit, not in `refund_net_loss`). Refund cap = `return_value + tax_share` (+ `shipping_net` when `refund_shipping`), see Tax on returns.
- Reports: **Returns** = value/qty of return documents; **Refunds** = money actually paid back. `refund_net_loss = return_shipping_cost` (the kept payment fee is already inside order profit; do not subtract twice — clarified 2026-10-21); the returned goods' profit is reversed: sales/profit reports subtract `return_value` and add back `returned cogs`.

## Flash sale
Price used while `now ∈ [start,end]`, `sold < qty_limit`. **Split, never reject:** if a line asks for more units than remain, the line is SPLIT into two order items — `remaining` units at the flash price and the rest at the regular price (extra qty is not refused). Sold counter increments on order placement (flash units only), decrements on cancel. **Across cart lines (2026-10-25):** units already given the flash price earlier in the SAME quote are consumed from the flash item's `remaining` (tracked per flash item id), so a product-wide item (`product_variant_id = 0`) shared by several variant lines never grants more than `remaining` flash units in total; extra units get the regular price. Placement uses the same locked quote and increments `sold` by exactly the flash units of each line (guarded: `sold + qty ≤ qty_limit`, else the placement is refused).

## Stock
`on_hand = Σ movements` per (branch, product/variant). Types: purchase_in, sale_out, return_in, transfer_out, transfer_in, adjustment_in/out. Reserve at order placement (`reserved`), deduct at shipped. `available = on_hand − reserved`. Never negative unless setting `allow_backorder`.
Weighted-avg cost on purchase_in: `new_avg = (on_hand×avg + qty×cost)/(on_hand+qty)`.
Stock valuation = `Σ on_hand × avg_cost`.
**Landed costs (ERP setting `landed_costs`, ERP-019):** `expense` (default, unchanged business costing) = PO shipping/other costs are not in unit cost (ledger: purchase expenses); `capitalise` (IAS 2) = they are allocated to the PO lines by line value (cent-rounded, last line takes the remainder) and the `purchase_in` unit cost = `(line_value + share)/qty`; the ledger posts inventory = Σ received movement value and any cent residue to purchase expenses.
Implementation (`App\Services\Stock\StockLedger`, the only writer of stock): avg is kept per (branch, product, variant) in `stock_levels`; incoming types (purchase_in, transfer_in, return_in, adjustment_in) re-average, outgoing types are valued at current avg and leave it unchanged; if `on_hand ≤ 0` before an incoming row, avg = incoming cost. Transfers move stock at the source avg (snapshotted on the transfer item). After `purchase_in`, the listing `cost` (`products.cost` / `product_variants.cost`) = `Σ(on_hand×avg)/Σ on_hand` across branches (this is the order `unit_cost` snapshot). PO shipping/other costs are NOT allocated into unit cost (only in PO `total_cost` for the Purchases report). Negative stock refused unless setting `allow_backorder`.

## Bundles (fixed-price packs; added 2026-10-30)
A bundle is a merchant-defined pack of N component lines (`bundle_items`: product, variant or 0, `quantity` per bundle) sold at ONE fixed `bundle.price` (> 0, shop currency). It is a cart/storefront concept only: **at quote/placement it is expanded into ordinary component order lines**, so stock, COGS, discount scopes, returns, profit, commission and reports need no special case.
- **Price allocation (cent-exact).** For a bundle line of `q` bundles: `T = bundle.price × q`; component `i` has `n_i = qty_per_i × q` units and weight `w_i = regular_unit_price_i × n_i` (regular = `PriceResolver` price: `sale_price` else `price`, variant override; NEVER flash). `W = Σ w_i` (if `W = 0` weights are the unit counts). Share `s_i = round_half_up(T × w_i / W)` for every component except the last; each `s_i` is clamped to `[0, T − Σ previous]` and the LAST component takes the exact remainder `T − Σ previous`. So **Σ s_i = T exactly and no share is negative**, whatever the bundle price vs. the regular total (a bundle priced above its regular total is allowed).
- **Order lines.** A component share `s_i` over `n_i` units is stored as at most TWO `order_items` with whole-cent unit prices (like the flash-sale split): `base = floor(s_i×100 / n_i)` cents, `r = s_i×100 − base×n_i` cents → `r` units at `(base+1)` cents and `n_i − r` units at `base` cents (a single line when `r = 0`). Therefore `line_subtotal = unit_price × qty` stays exact for every line and `Σ line_subtotal` of the bundle's lines `= T`. Each line carries `bundle_id`, `bundle_name` (snapshot) and `bundle_group` (uuid, one per bundle cart line) for grouping in UI/invoice/API. `unit_cost` is the normal component cost snapshot ⇒ **COGS and profit of a bundle = Σ of its components**; `subtotal` = Σ lines includes `T`.
- **Flash sale / discounts.** A flash sale NEVER applies to bundle components and never consumes flash quantity (the bundle price is final). Discount codes see the component lines as ordinary lines at their ALLOCATED unit price (scope products/categories match the component product; `min_order` uses the subtotal as before); the discount is distributed per line by the existing proportional rule.
- **Tax, shipping, fees, commission.** Unchanged: they work from `subtotal`/lines, which already hold the allocated prices.
- **Returns.** Per component line, exactly as today (`return_value = unit_price × qty − discount_share`, cumulative rule). Returning one component of a bundle refunds ITS allocated price only; the other components are unaffected. UI groups the lines under the bundle name; there is no "return whole bundle" shortcut.
- **Stock.** Availability of a bundle = `min_i floor(available_i / qty_per_i)` over its components (branch-summed `on_hand − reserved`); with `settings.allow_backorder` bundle availability is unlimited. Checked at add-to-cart (cart total of that bundle + the new quantity, and the component demand of the whole cart) and again at placement: reservation goes through the normal per-product-variant reservation under the existing row locks (components of different cart lines are summed per product-variant). A bundle is purchasable only when `is_active`, inside `starts_at..ends_at` (when set), not soft-deleted, and EVERY component is a listed (active, priced) product/variant; otherwise add-to-cart is refused and an existing cart line makes the quote fail with "item unavailable".
- **Retention.** A soft-deleted bundle row is kept by the purger while any `order_items.bundle_id` references it.

## Special packaging (Feature 2; added 2026-10-31)
A shop-defined paid packaging option (`packaging_options`: `price` = customer fee, `cost` = merchant cost, default 0). One packaging per order (quantity 1); chosen at cart/checkout, snapshotted on the order: `packaging_option_id`, `packaging_name` (translations), `packaging_fee`, `packaging_cost`, `packaging_tax`. ONLY `OrderCalculator` does the math (`CalculatorInput::packagingFee/packagingCost`).
- **Own step in the total.** `packaging_fee` is NOT part of `subtotal`, so it is never discountable (discount base = goods only; min_order and scopes see goods only), and it is NOT part of the free-shipping threshold (`subtotal − discount ≥ free_over` unchanged) nor of the COD-fee `free_over` test. No packaging ⇒ every number is exactly as before.
- **Tax.** `packaging_tax` is stored separately; `orders.tax` stays the tax on GOODS only (so returns, revenue and the inclusive detection keep their meaning). Exclusive prices: `packaging_tax = packaging_fee × r` and it is ADDED to the total (tax base += packaging_fee). Inclusive prices: `packaging_tax = packaging_fee × r/(1+r)`, already inside `packaging_fee`, not added. Customer-facing "tax" lines show `tax + packaging_tax`.
- **Fee bases.** Payment-fee and COD-fee base `F = subtotal − discount + shipping_net + tax_added + packaging_fee + packaging_tax_added` (customer pays the packaging online/COD like everything else).
- **Total** `= subtotal − discount + shipping_net + tax_added + packaging_fee + packaging_tax_added + payment_fee_charged + cod_fee`. `cod_amount = total − prepaid_shipping` therefore includes the packaging; `prepaid_shipping` is unaffected.
- **Inclusive detection from stored columns:** `tax + packaging_tax > 0` and `total − (subtotal − discount + shipping_net + payment_fee_charged + cod_fee + packaging_fee) < tax + packaging_tax` (exclusive orders have the difference `= tax + packaging_tax`; inclusive `= 0`). Used by `Order::taxIncluded()`, `ReturnService::taxShare` and the SQL in `ReportRepository`.
- **Profit.** `packaging_revenue = packaging_fee − (inclusive ? packaging_tax : 0)` (VAT is never revenue); `order_net_profit += packaging_revenue − packaging_cost`. Recognised on admin confirmation like other income. Commission base (goods) is unchanged.
- **Returns / cancel.** NOT refunded on partial returns (kept like the COD fee): refund cap `= return_value + tax_share (+ shipping_net)` unchanged, `tax_share` uses goods tax only, its inclusive detection excludes packaging. Refunded only when the whole order is cancelled before shipping (it is part of `total`, refunded like all other money). A cancel/full-return removes the order from sales and profit, packaging included.
- **Reports.** Sales report gets a `packaging_fee` column/card/CSV (`Σ packaging_fee`, customer-charged, included in `total`); Net profit report adds a `Packaging` income line `Σ (packaging_fee − inclusive packaging_tax − packaging_cost)` and the net-profit formula includes it.
- **Retention.** A soft-deleted packaging option is kept by the purger while any order references it.
- **Worked example.** Order of the worked example below (subtotal 250, discount 20, shipping 30, card fee 2.5%+1 customer-borne) plus packaging price 15 / cost 4, tax 0: F = 230+30+15 = 275 → fee = 6.875+1 = 7.88 (half-up 7.875); total = 275 + 7.88 = 282.88; discount and shipping unchanged (free-shipping threshold uses 230). profit = 73.50 + (15 − 4) = **84.50** (the customer-borne payment fee still nets to 0; commission unchanged at 11.50). Tax-exclusive 14%: goods tax = 230×14% = 32.20, packaging_tax = 2.10, total tax 34.30. Tax-inclusive 14%, packaging 114: packaging_tax = 114×14/114 = 14.00, not added; packaging revenue = 100.00 (minus cost).

## Reports (date range on `created_at` of the document unless stated; sales AND profit use admin-confirmed orders: status ∈ {confirmed, processing, shipped, delivered} — updated 2026-10-21)
- **Purchases**: total_cost = Σ purchase_items qty×cost (+ shipping/other costs on PO); cards: #POs, qty, avg cost, top suppliers.
- **Sales**: total = Σ total; costs = Σ cogs; discounts = Σ discount; shipping = Σ shipping_net; fees = Σ payment_fee (payment fees only); **cod_fee = Σ cod_fee** (customer-borne COD extra fee, separate column/card, never mixed into fees; included in `total`); net profit per Profit formula.
- **Discounts**: Σ discount + usage per code. **Shipping costs**: Σ shipping_cost vs Σ shipping_net collected per company. **Payment fees**: Σ fee by method (+ bearer split).
- **Net profit** period formula above. **Returns/Refunds** per definitions. **Expenses**: Σ amount by category.
- **No aggregate across stores** (single shop): every report sums amounts in the shop currency as stored; nothing is converted.

### Reports as implemented (Phase 6, `App\Services\Reports\ReportService` + `ReportRepository`)
- Date range = `created_at` of the document (expenses: `expense_date`; refunds: `refunded_at`/`cancelled_at`); stock is a snapshot. Sales statuses = confirmed, processing, shipped, delivered; **profit from all admin-confirmed orders (same set) created in the range** — CHANGED 2026-10-21 from delivered-only (`orders.net_profit` snapshot must be computed at confirmation; returns reduce it).
- Purchases = RECEIVED POs only (`total_cost` incl. shipping/other). Returns = documents in status approved|refunded.
- Net profit = Σ admin-confirmed (confirmed|processing|shipped|delivered) `(subtotal−discount−tax_in_goods) − cogs + shipping_net − shipping_cost − (payment_fee − payment_fee_charged) − affiliate_commission` − Σ(`return_value − return_tax_incl − returned_cogs`) [returns of sales-set orders only] − Σ`return_shipping_cost` [all approved/refunded returns] − Σ expenses. The kept payment fee is already inside the order profit, so it is NOT subtracted again as refund loss (`refund_net_loss` = return shipping cost).
- Top products/categories: qty/revenue/cost/profit are net of returned qty (`line_subtotal − line_discount` pro-rated by `(qty−returned)/qty`); a product in several categories counts in each. Low stock: `on_hand − reserved ≤ settings.low_stock_threshold` (default 5).
- Sales report columns (daily rows, cards, CSV): day, orders, subtotal, total, cogs, discount, shipping, fees (payment fees), **cod_fee**, net_profit. `cod_fee` is charged-to-customer only (merchant bearer ⇒ 0).
- Branches report: `profit = Σ orders.net_profit` over the same admin-confirmed set (not delivered-only).
- Carrier settlement report AND the "Mark carrier settled" action respect the report's branch filter (`orders.branch_id`).
- Money SUMs are `ROUND(SUM(col), 2)` in SQL in the shop currency (the former cross-store `× currency_rate` normalisation and base currency were removed with multi-tenancy, 2026-11-06).

## Order attribution, Gift Finder and customer cancellation (P2, 2026-11-08: the n8n Growth system was removed)
The former "Growth system definitions" (contribution-margin metrics, guardrails, inventory / capital engine, supplier price ranking, return-intel fix
tasks, ambassador reward ledger, ad-spend caps, bundle A/B, Hijri task reminders, classifier) were deleted with the Growth module (MARKETER_PLAN.md P2);
none of them fed an order, cart, payout, stock or ERP figure. The ambassador reward ledger (only active with the `ambassadors` switch ON) is dropped with its table; the `ambassador_rewards`
ERP posting path is removed; historical journal entries with source `ambassador_rewards` (if any) stay as posted. What remains:
- **Channel / first-touch attribution** (`App\Services\Storefront\AttributionService`, middleware `attribution.capture` on storefront pages, header
  `X-Attribution` on the mobile API): captured once per browser session from utm_*, `ref`, gclid/fbclid presence (presence only) or an external referrer host;
  copied at placement to `orders.attribution` (+ `gift_session` id when the cart was prepared by the Gift Finder) and `orders.channel`
  (affiliate > paid (gclid/fbclid/cpc) > email > social > search > other utm > referrer host (search/social/referral) > direct; an affiliate always wins).
  Mobile: first touch stored on `carts.attribution`. Display/analytics only; never changes a price, fee or commission. Bots ignored; no IP / UA stored.
- **Gift Finder ranking** (`App\Services\GiftFinder\GiftScorer`, weights in `config/gift_finder.php`; P3 2026-11-08: products AND bundles in ONE list).
  Hard filters (an item failing one is never offered): active; in stock (product: sum of branch `on_hand` > 0; bundle: purchasable per BundleResolver —
  live, every component listed — and `min_i floor((on_hand − reserved)_i / qty_per_i) > 0` over active branches, unlimited with `allow_backorder`);
  restriction words (product name / bundle name / any item name); once any product is tagged `gift_suitable` only tagged products and bundles with at
  least one tagged item; recipient (product tagged for other people; bundle: ANY item tagged for other people); occasion (product tagged for other
  occasions only — no occasion tag = any occasion; bundle: EVERY item tagged for other occasions only); chosen category incl. sub-categories (product
  not in it; bundle with no item in it). Price = product `sale_price` else `price`; bundle = `bundle.price`.
  - **Product fit** (max 100) = `category (30 when a category is chosen — every survivor is in it —, else 15) + recipient tag (25) + occasion tag (20)
    + 15 × price/budget + 10 × sold/max_sold`.
  - **Bundle fit** (max 105) = `30 × share of items in the chosen category (15 when none chosen) + 25 × share of items tagged for the recipient
    + 20 × share of items tagged for the occasion + 15 × price/budget + 10 × bundles_sold/max_sold + 5 × min(1, savings% / 30)`, where
    share = matching items / items, savings% = (regular_total − price) / regular_total × 100 (regular_total = Σ PriceResolver price × qty per bundle,
    the bundle page's "old price"), bundles_sold = floor(Σ component units of its order lines / Σ qty per bundle).
  - sold = units (product) / whole bundles in delivered orders placed in the last `popularity_days` = 30; `max_sold` is shared by products and bundles.
  - Order: `round(fit/5)` bucket desc, then margin % desc (product `(price − cost)/price`, bundle `(price − Σ cost×qty)/price`) ONLY as a tie-breaker,
    then products before bundles, then id. Prefers items ≥ 20% of the budget unless fewer than 3 qualify. Main list `items` = top `max_items` (12),
    **always price ≤ budget** whatever the sort; `sort=price_asc|price_desc` only reorders those best matches. `type=products|bundles` filters the list.
  - **Near budget**: items with budget < price ≤ 1.25 × budget, cheapest first (3), flagged `over_budget`, never mixed into the main list.
  - **Relaxation** when the main list is empty: drop the category, retry; still empty → drop the occasion too; the response lists `relaxed`
    (`category`, `occasion`) and a notice. Recipient and restriction words are never relaxed.
  - Legacy API arrays: `results` = top 8 products, `bundles` = top 3 bundles, `near_budget` = near-budget products (same rules).
- **Gift Finder stats** (`GiftFinderService::stats`, admin + integration API): sessions in the last N days; completion = sessions with results / sessions;
  cart rate = sessions with a prepared cart / sessions with results; gift orders = orders with `attribution.gift_session` placed in the window and not
  cancelled; AOV = their average `total`; order rate = gift orders / sessions with a cart. P3: `bundle_sessions` = sessions that suggested a bundle,

- **Customer cancellation** (setting `customer_cancel.enabled`, Settings → General, default OFF; formerly behind the Growth `return_intel` switch): the owner of an

## Marketing analytics (marketer panel + `/api/internal/marketing`, P4 2026-11-08)
Read-only, never re-implements order math (`App\Services\Marketing\MarketingAnalyticsService`; full spec docs/marketing/API_DOCUMENTATION.md §3, §5).
- Store figures come from the Reports module: sales set + date bucket as §Reports, `gross_sales = Σ total` (Sales report), `revenue_goods` / net profit = Net profit report (`ReportService::netProfitFigures`).
- Item revenue per product = the Top products definition `(line_subtotal − line_discount) × (qty − returned_qty) / qty` (VAT included for tax-inclusive shops ⇒ warning).
- **Gross profit (marketing)** = item revenue of lines with `unit_cost > 0` − Σ `unit_cost × net qty` of those lines; `cost_coverage_percent` = costed item revenue / item revenue × 100. A line with `unit_cost = 0` is "uncosted" (missing data): excluded, never estimated; `gross_profit = null` when nothing is costed. Net profit is shown only at 100 % coverage. Contribution profit, ad spend, ROAS, CAC = null until an ad source exists.
- Listing margin % = (effective price − listing cost) / effective price × 100 (listing cost 0 ⇒ unknown). Flash-sale item `negative_margin` = flash price (PriceResolver::flashPrice) < listing cost. Bundle margin = (bundle.price − Σ component cost × qty) / bundle.price (unknown if any component has no cost).
- Campaign-candidate score = 35·velocity + 30·margin + 20·stock_cover + 15·recency (`CampaignScorer`, components 0..1, deterministic tie-break available desc, id asc).
- **Suggestion margin guards (P5, Suggestions Center — checks only, no order math changes):** bundle suggestion margin = (bundle price − Σ component listing cost × qty) / price: < 0 refused, < `marketing.suggestions.min_margin_percent` (10) or a component without cost ⇒ warning. Offer (flash sale) suggestion: flash price per `PriceResolver::flashPrice` semantics (percent off the regular price, or a fixed price, never above regular) below the item's listing cost ⇒ refused. Coupon suggestion: worst case = a one-unit order of each in-scope active product (scope all / products / categories incl. sub-categories) — percent: `price − min(price × value%, max_discount)`, fixed: `price − min(value, price)` only for products with price ≥ min_order; a product with an active flash sale overlapping the coupon window is checked at its flash price (flash + coupon stack); result below listing cost ⇒ refused; products without cost are skipped with a warning; free-shipping codes ⇒ warning only.

## ERP financial reports (Phase 7)
The ERP reports/dashboard never recompute order math: they sum posted journal lines (docs/ERP_PLAN.md section 8). The Financial Reconciliation report compares those sums with the Net Profit report and order/purchase/stock records; differences are reported, not adjusted.

### ERP revenue recognition (2026-11-04, audit ERP-002/011 - supersedes "revenue at confirmation" for the ledger)
ERP setting `revenue_recognition` (ERP Settings):
- **`shipped` (default for a new ledger)** - IFRS 15 control transfer when the parcel leaves the warehouse. The recognition entry (key `order:{id}:confirm`, historical name) holds revenue, VAT, shipping/fee/packaging income, shipping cost, COD/wallet payment fee, affiliate commission and **COGS = `orders.cogs` after the shipment re-valuation = Σ sale_out movement value**, Cr Inventory. Ledger inventory therefore equals the stock valuation at all times (no "committed" gap). Confirmed/processing orders carry nothing but their prepayments (customer credit on Receivable).
- **`delivered`** - control on delivery: at shipment `Dr Goods out for delivery (1320) / Cr Inventory` (key `order:{id}:ship`); on delivery the recognition entry takes COGS from Goods out for delivery.
- **`confirmed`** (legacy; pinned automatically when order journals already existed - migration `2026_12_17_100001`) - recognition at admin confirmation with the cost snapshot; at shipment a COGS true-up `order:{id}:cogs-trueup` = shipped cost − booked COGS.
Cancel before recognition posts nothing; cancel after it (incl. returned-to-sender) reverses the recognition family (`confirm`, `ship`, `cogs-trueup`, `commission:*`). The **Net Profit report keeps the admin-confirmation rule** (management report): the ERP Reconciliation report removes confirmed-but-not-yet-recognised orders from its expected side (revenue, COGS, net profit, receivable) - a timing difference, not a mismatch.
Other ledger rules from the audit: packaging cost is `Dr Packaging / Cr Packaging supplies (1330)` (packaging is never a stock item; map the packaging purchase category to 1330 to capitalise it) (ERP-008); an online gateway fee is booked when the money arrives (`order:{id}:gateway-fee`, Dr Gateway fees / Cr Gateway) and is NOT reversed on cancel - the provider keeps it (ERP-023); a COD-method payment fee is credited to Shipping payable (charged by the carrier) (ERP-023); a PAID affiliate commission is never reversed by a later return (ERP-004).

### ERP inventory reconciliation (Phase 9)
Ledger inventory is expected to equal the stock valuation. Only under the legacy `confirmed` policy is stock deducted at shipping while COGS is booked at confirmation; then `expected = stock valuation - COGS of confirmed/processing orders posted but not yet deducted` ("committed", packaging excluded since packaging is not inventory).

### ERP ledger integrity (Phase 10)
`erp:verify` audits the ledger against itself (posted entries balance, cached `current_balance` = balance recomputed from lines, no orphan lines, unique idempotency keys/numbers); `erp:reconcile` compares it with business records. Run both after any backfill and weekly (verify is scheduled). Both exit non-zero on a mismatch.

### ERP exchange rates (single store, 2026-11-06)
`erp_exchange_rates` (ERP Settings → Exchange rates card, perm `erp.settings.manage`) stores reference rates `1 from = rate to` from an effective date, for documents issued in a foreign currency. They are informational: the ledger, every ERP report and every sales report stay in the shop currency (`setting('currency_code')`), and no amount is converted automatically (the only former consumer, the cross-store consolidated view, was removed with multi-tenancy). A journal keeps its own `currency` / `exchange_rate` columns (default the shop currency, rate 1).
